# Проектирование высоконагруженного dating-сервиса

## 1. Тема и целевая аудитория

### 1.1. Тема

Dating-приложение для пользователей EU-27.

Основной проектируемый контур:

**Discovery → Like/Pass → Match**.

Аналоги: Tinder, Bumble, Hinge.

### 1.2. Целевая аудитория

| Параметр | Значение |
|---|---|
| Регион | EU-27 |
| Население региона | ~450,4 млн [1] |
| Возраст | 18–39 лет |
| Аудитория аналога | 10 млн еженедельно активных пользователей Tinder в Европе [2] |

EU-27 выбран как единый регион: большая часть аудитории находится в близких часовых поясах, поэтому регион удобен для дальнейшего анализа суточного профиля нагрузки.

### 1.3. Функционал MVP

1. **Профиль и предпочтения**
   - фотографии и основная информация;
   - пол и предпочтения;
   - возрастной диапазон;
   - максимальная дистанция поиска.

2. **Обновление местоположения**
   - хранение актуальной геопозиции пользователя;
   - использование геопозиции при подборе кандидатов.

3. **Discovery**
   - формирование персонализированной ленты анкет;
   - фильтрация по расстоянию, возрасту и предпочтениям;
   - исключение уже просмотренных анкет;
   - ранжирование кандидатов.

4. **Like / Pass**
   - сохранение реакции пользователя на анкету.
   - отправка уведомления пользователю при получении Like.

5. **Match**
   - автоматическое создание Match при взаимном Like;
   - не более одного Match для одной пары пользователей.
   - отправка уведомления пользователю при создании Match.

6. **Список Match**
   - получение списка взаимных совпадений пользователя.

### 1.4. Ключевые продуктовые решения

- Discovery формируется сервером, пользователь не выполняет произвольный поиск по базе анкет.
- География, возраст и предпочтения используются при отборе кандидатов [3].
- Уже обработанные через Like/Pass анкеты повторно в обычной ленте не показываются.
- Match создаётся только при взаимном Like [4].
- Точная геопозиция пользователя другим пользователям не раскрывается.
- Ранжирование выполняется на сервере; ML-модель не является обязательной частью MVP.
- Чат, платежи, звонки и рекламная система не входят в MVP.

## 2. Расчет нагрузки

В разделе рассчитываются продуктовые и технические метрики для основного контура сервиса **Discovery → Like/Pass → Match**.

### 2.1. Аудитория

В качестве верхней оценки месячной аудитории используется официальное раскрытие Tinder по требованиям DSA: за период с 1 июля по 31 декабря 2025 года среднемесячное количество активных получателей Tinder в ЕС было **менее 15 млн** [5]. Для проектирования принимается верхняя граница:

`MAU = 15 млн пользователей`.

Публичного актуального DAU для всего ЕС Tinder не раскрывает. Для оценки отношения `DAU / MAU` используются данные Ofcom / Ipsos iris по Великобритании за май 2023 года: месячная аудитория Tinder составила 2,487 млн пользователей, средняя дневная аудитория — 899 тыс. [6].

![UK online adult reach of Tinder](images/uk_tinder_reach.png)

`DAU / MAU = 899 000 / 2 487 000 ≈ 0,361 = 36,1%`

`DAU = 15 000 000 × 0,361 = 5 415 000`

Таким образом, для дальнейших расчётов принимается:

| Метрика | Значение |
|---|---:|
| MAU | 15 млн |
| DAU | 5,415 млн |
| DAU / MAU | 36,1% |

Перенос коэффициента `36,1%` с Великобритании на EU-27 является расчётной экстраполяцией.

### 2.2. Продуктовые метрики

#### 2.2.1. Like / Pass

Под Like/Pass понимается суммарное количество положительных и отрицательных реакций на показанные анкеты.

По внутренним данным Tinder, в 2024 году пользователи отправляли почти **16 млрд Likes/Pass в неделю** [7]. Tinder также указывает аудиторию около **50 млн пользователей в месяц** по всему миру [8].

Среднее количество реакций на одного пользователя месячной аудитории в сутки:

`16 000 000 000 / 7 / 50 000 000 ≈ 45,7 Like/Pass`

Для проектируемого сервиса:

`15 000 000 × 45,7 ≈ 685,7 млн Like/Pass в сутки`

В пересчёте на одного DAU:

`685,7 млн / 5,415 млн ≈ 126,6 Like/Pass на активного пользователя в сутки`

#### 2.2.2. Использования приложения

По данным Nielsen Digital Japan за апрель 2025 года, Tinder использовался в среднем **52 раза в месяц на пользователя** [9].

Для расчётного месяца в 30 дней:

`52 / 30 ≈ 1,73 использования приложения на MAU в сутки`

или:

`1,73 / 0,361 ≈ 4,8 использования на DAU в активный день`

Для операций, выполняемых при каждом новом использовании приложения, в проекте принимается правило: клиент один раз обновляет актуальную геопозицию и один раз синхронизирует первую страницу списка Match.

#### 2.2.3. Discovery

Для проектируемого сервиса выбирается небольшая пачка Discovery:

`до 10 анкет / запрос`.

Размер 10 является проектным решением: он ограничивает объём неиспользованных рекомендаций и позволяет чаще обновлять подбор, сохраняя пакетную выдачу. Ответ содержит данные анкет и ссылки на фотографии. Клиент загружает первые фотографии текущей и двух следующих карточек; остальные фотографии — по мере просмотра. Отложенная загрузка изображений уменьшает лишний сетевой трафик [14].

Клиент сохраняет неиспользованные анкеты между сессиями и запрашивает следующую пачку, когда остаётся три карточки. При изменении местоположения или предпочтений буфер сбрасывается. Для базового расчёта принимаются полные пачки и их последующее использование:

`685,7 млн / 10 ≈ 68,57 млн Discovery-запросов в сутки`

Неполные ответы, сброс буфера и повторные запросы увеличивают фактический RPS относительно этой оценки.

На одного пользователя MAU:

`45,7 / 10 ≈ 4,57 Discovery-запроса в сутки`

#### 2.2.4. Match

Для оценки частоты Match используются более свежие внутренние данные Tinder за 2024 год. Tinder указывает, что на Dating Sunday создавалось около **380 Match в секунду**, что примерно на 9% выше обычного уровня года [16]. Следовательно, обычный уровень:

`380 / 1,09 ≈ 348,6 Match/с`

`348,6 × 86 400 ≈ 30,12 млн Match/сутки`

С учётом почти 16 млрд Like/Nope в неделю [7]:

`30,12 млн / (16 млрд / 7) ≈ 1,318%`

Для проектируемого сервиса:

`685,7 млн × 1,318% ≈ 9,04 млн новых Match/сутки`

Одна физическая запись Match относится к одной паре пользователей. В среднем это:

`9,04 млн / 15 млн ≈ 0,602 создаваемого Match на MAU в сутки`

Поскольку один Match появляется в списках двух пользователей:

`2 × 0,602 ≈ 1,205 нового элемента Match List на пользователя в сутки`

#### 2.2.5. Сводная таблица продуктовых метрик

| Метрика | Значение |
|---|---:|
| MAU | 15 млн |
| DAU | 5,415 млн |
| Like/Pass на MAU в сутки | ≈45,7 |
| Like/Pass на DAU в сутки | ≈126,6 |
| Like/Pass всего в сутки | ≈685,7 млн |
| Использований приложения на MAU в сутки | ≈1,73 |
| Discovery-запросов на MAU в сутки | ≈4,57 |
| Location Update на MAU в сутки | ≈1,73 |
| Match List на MAU в сутки | ≈1,73 |
| Создаваемых Match на MAU в сутки | ≈0,602 |
| Новых элементов Match List на пользователя в сутки | ≈1,205 |

### 2.3. Средний размер хранилища пользователя

#### 2.3.1. Фотографии

В исследовании 307 Tinder-профилей пользователей 18–30 лет из Бельгии среднее количество фотографий в профиле составило **4,79** [10]. Это значение принимается как среднее количество фотографий на пользователя.

В открытом дампе Tinder API для одной пользовательской фотографии присутствуют original-файл и четыре обработанных WebP-варианта:

- `640×800`;
- `320×400`;
- `172×216`;
- `84×106`;

для WebP указан `quality factor = 75` [11].

Для проектируемого сервиса принимается аналогичная модель хранения. После preprocessing original/canonical JPEG ограничивается **2 МБ**. Это проектное ограничение обосновывается практикой хранения изображений в других массовых сервисах: например, схема Bluesky для raw image blob устанавливает максимальный размер 2 МБ [12].

Для оценки четырёх WebP-копий используется исследование Google WebP: для фотографических наборов Kodak и Tecnick при качестве, соответствующем JPEG Q=75, средняя плотность находится примерно на уровне 0,51–0,63 бит/пиксель [13]. Чтобы не занижать объём, в capacity planning принимается консервативный бюджет **1 бит/пиксель**.

Общее количество пикселей четырёх вариантов:

`640×800 + 320×400 + 172×216 + 84×106 = 686 056 пикселей`

При 1 бит/пиксель:

`686 056 / 8 ≈ 85,8 КБ`

После округления с запасом принимается:

`≈0,10 МБ на все четыре WebP-варианта`

Полный storage budget одной фотографии:

`2,00 + 0,10 = 2,10 МБ`

Средний пользователь:

`4,79 × 2,10 ≈ 10,06 МБ = 0,01006 ГБ`

При этом одна логическая фотография представлена пятью физическими объектами, поэтому:

`4,79 × 5 ≈ 23,95 image objects на пользователя`

#### 2.3.2. Like / Pass

Для Like/Pass принимается rolling retention **12 месяцев**: система хранит только реакции за последний год. Это ограничивает неограниченный рост истории реакций. Для пользователя такой срок не должен быть существенной проблемой: спустя год ранее просмотренная анкета уже может заметно измениться, а сам факт её прежнего просмотра с высокой вероятностью будет забыт. После удаления старой реакции анкета снова может попасть в Discovery.

Среднее число реакций на одного пользователя за 12 месяцев:

`45,7 × 365 ≈ 16 686 записей`

Логическая запись реакции содержит:

| Поле | Размер |
|---|---:|
| `user_id` | 8 Б |
| `target_user_id` | 8 Б |
| `reaction` | 1 Б |
| `created_at` | 8 Б |
| **Итого** | **25 Б** |

Средний логический объём Like/Pass на пользователя:

`16 686 × 25 ≈ 417 150 Б ≈ 0,000417 ГБ`

#### 2.3.3. Match

Match хранится бессрочно, поскольку является пользовательским состоянием. Для одной пары достаточно двух идентификаторов пользователей и времени создания:

| Поле | Размер |
|---|---:|
| `user_a_id` | 8 Б |
| `user_b_id` | 8 Б |
| `created_at` | 8 Б |
| **Итого** | **24 Б** |

За первый год создаётся:

`9,04 млн × 365 ≈ 3,30 млрд Match`

На одного пользователя приходится около 440 элементов Match List за год, но одна физическая запись хранится только один раз на пару. В пересчёте на долю физического storage это около **5,3 КБ на пользователя за год**.

#### 2.3.4. Сводная таблица хранения на пользователя

| Тип данных | Количество на пользователя | Объём на пользователя |
|---|---:|---:|
| Фотографии | 4,79 фото / ≈23,95 image objects | ≈0,01006 ГБ |
| Like/Pass за последние 12 мес. | ≈16 686 записей | ≈0,000417 ГБ |
| Match, первый год | ≈440 элементов в списке | ≈0,0000053 ГБ |
| **Итого** | — | **≈0,01048 ГБ** |

Профиль, предпочтения и текущая геопозиция занимают на порядки меньше места по сравнению с фотографиями и историей реакций.

### 2.4. Общий размер хранилища

Для расчёта продуктового хранилища принимается 15 млн хранимых активных профилей. Архивирование удалённых и длительно неактивных аккаунтов находится за рамками MVP.

Фотографии:

`15 млн × 4,79 = 71,85 млн логических фотографий`

`71,85 млн × 5 = 359,25 млн image objects`

`71,85 млн × 2,10 МБ ≈ 150,89 ТБ`

Like/Pass:

`685,7 млн × 365 ≈ 250,29 млрд записей`

`250,29 млрд × 25 Б ≈ 6,26 ТБ`

Match за первый год:

`≈3,30 млрд × 24 Б ≈ 0,079 ТБ`

| Тип данных | Количество | Объём |
|---|---:|---:|
| Фотографии | 71,85 млн фото / 359,25 млн объектов | ≈150,89 ТБ |
| Like/Pass, rolling window 12 мес. | ≈250,29 млрд записей | ≈6,26 ТБ |
| Match, первый год | ≈3,30 млрд записей | ≈0,079 ТБ |
| **Итого** | — | **≈157,23 ТБ** |

При стабильной аудитории объём фотографий и Like/Pass выходит на стационарный уровень. Match хранится бессрочно и добавляет примерно `0,079 ТБ/год`.

### 2.5. Суточный профиль и коэффициент пиковой нагрузки

Для оценки обычного суточного пика используется опубликованный MarketingProfs график на основе **Nielsen Electronic Mobile Measurement**. Nielsen измерял использование приложений пассивным мониторингом смартфонов пользователей в США. Для Tinder максимум приходится на вечернее время; час 22:00–23:00 является пиковым [15].

![Daily Tinder and OkCupid Usage Trends](images/tinder_daily_usage_trends.png)

*Рисунок — суточный профиль использования Tinder и OkCupid по данным Nielsen Smartphone Analytics [15].*

По графику на пиковый час Tinder приходится примерно **7,7%** суточного времени использования. Среднее значение для одного часа:

`100% / 24 ≈ 4,167%`

Коэффициент пикового часа:

`K_peak = 7,7 / 4,167 ≈ 1,85`

Современные внутренние данные Tinder дополнительно подтверждают вечерний характер пика: наиболее загруженные часы приходятся примерно на 21:00–22:00 local time [17].

Для расчётов принимается:

`K_peak = 1,85`

### 2.6. RPS

#### 2.6.1. Like / Pass

`685,7 млн / 86 400 ≈ 7 937 RPS`

Пик:

`7 937 × 1,85 ≈ 14 683 RPS`

#### 2.6.2. Discovery

`68,57 млн / 86 400 ≈ 794 RPS`

Пик:

`68,57 млн / 86 400 × 1,85 ≈ 1 468 RPS`

#### 2.6.3. Location Update

При каждом использовании приложения выполняется одно обновление геопозиции.

`15 млн × 52 / 30 = 26 млн запросов/сутки`

`26 млн / 86 400 ≈ 301 RPS`

Пик:

`301 × 1,85 ≈ 557 RPS`

#### 2.6.4. Match List

При каждом использовании приложения клиент один раз синхронизирует актуальный список Match:

`26 млн запросов/сутки`

`≈301 RPS average`

`≈557 RPS peak`

#### 2.6.5. Match creation

Создание Match не является отдельным внешним HTTP-запросом: оно выполняется внутри обработки Like при обнаружении встречного Like.

`9,04 млн / 86 400 ≈ 105 событий/с`

Пик:

`105 × 1,85 ≈ 193 события/с`

Эта нагрузка учитывается как внутренняя и не прибавляется повторно к внешнему API RPS.

### 2.7. Сетевой трафик

В отчёте data.ai *State of Mobile 2022* для Tinder указано около **190 МБ мобильного трафика на активного пользователя в месяц** в 2021 году; данные относятся к Android [18].

Для нашей аудитории:

`15 млн × 190 МБ / 30 ≈ 95 000 ГБ/сутки`

То есть:

`≈95 ТБ/сутки`

Средняя пропускная способность:

`95 000 × 8 / 86 400 ≈ 8,80 Гбит/с`

Пиковая:

`8,80 × 1,85 ≈ 16,27 Гбит/с`

Значение 190 МБ/месяц дополнительно проверяется более свежими источниками. Ofcom сообщает, что в мае 2024 года средний посетитель Tinder в Великобритании провёл в сервисе около **1 часа 3 минут** [19]. В тестах Sim Local 2025 года десять минут свайпинга в Tinder потребляли 29,7–49,5 МБ [20]. Эти измерения дают сопоставимый порядок месячного трафика.

#### 2.7.1. Разбивка media-трафика

Для основного экрана Discovery обязательно загружается как минимум первая фотография каждой обработанной анкеты. Для WebP-варианта `640×800` при принятом консервативном бюджете 1 бит/пиксель:

`640 × 800 / 8 = 64 000 Б ≈ 64 КБ`

Тогда минимальный трафик первых фотографий:

`685,7 млн × 64 КБ ≈ 43 886 ГБ/сутки`

Средняя пропускная способность:

`≈4,06 Гбит/с`

Пиковая:

`≈7,52 Гбит/с`

Оставшаяся часть общего traffic budget включает дополнительные фотографии профилей, JSON/metadata Discovery, Like/Pass, Location, Match List, HTTP/TLS overhead и прочий небольшой трафик:

`95 000 - 43 886 ≈ 51 114 ГБ/сутки`

| Тип трафика | ГБ/сутки | Средний Гбит/с | Пиковый Гбит/с |
|---|---:|---:|---:|
| Первые фото Discovery | ≈43 886 | ≈4,06 | ≈7,52 |
| Дополнительные фото + API/metadata + protocol overhead | ≈51 114 | ≈4,73 | ≈8,76 |
| **Итого** | **≈95 000** | **≈8,80** | **≈16,27** |

Полученная разбивка показывает, что фотографии являются существенным источником сетевой нагрузки.

## 3. Глобальная балансировка нагрузки

Целевая аудитория сервиса размещена в EU-27. В разделе определяется схема глобальной доставки динамических API-запросов и фотографий профилей, а также необходимость географического распределения API между несколькими регионами.

| Пиковый Location Update RPS | ≈557 |
| Пиковый Match List RPS | ≈557 |
| Общий пиковый сетевой трафик | ≈16,27 Гбит/с |
| Минимальный пиковый трафик первых фотографий Discovery | ≈7,52 Гбит/с |

Доля Like/Pass в пиковом внешнем API-трафике:

`14 683 / 17 265 ≈ 85,0%`

Следовательно, основная API-нагрузка имеет write-heavy профиль.

### 3.2. Функциональное разбиение по доменам

Используются два публичных домена:

| Домен | Назначение | Тип нагрузки | Глобальная доставка |
|---|---|---|---|
| `api.example.com` | Discovery, Like/Pass, Location Update, Match List, профиль | динамические персонализированные запросы | три активных региона: Frankfurt, Paris, Milan |
| `media.example.com` | фотографии профилей | статический кэшируемый контент | CDN + Anycast |

Фотографии выносятся в CDN, поскольку CDN хранит копии контента на географически распределённых edge-узлах, уменьшая задержку доставки и нагрузку на origin [29].

### 3.3. Выбор количества регионов

Для сервиса принимается требование: **отказ одного региона не должен останавливать основной контур или приводить к потере подтверждённых Like и Match**. Потеря реакции может привести к пропуску взаимного совпадения, поэтому сохранность этого состояния важнее минимальной задержки записи.

Multi-AZ закрывает отказ отдельной зоны, но не общий отказ региона; для такого сценария AWS рекомендует межрегиональное резервирование [23]. Возможные варианты:

| Вариант | Оценка |
|---|---|
| Один регион с несколькими AZ | полный отказ региона останавливает сервис |
| Два региона с асинхронной репликацией | обеспечивают резервирование, но последние подтверждённые записи могут ещё отсутствовать во втором регионе |
| Два региона с синхронной записью в оба | сохраняют подтверждённые данные, но при отказе одного региона такая запись останавливается |
| Три региона с межрегиональным кворумом | позволяют сохранять подтверждённые данные и продолжать запись после отказа одного региона |

Выбраны **три активных региона**. Это минимальное число независимых региональных участников для большинства `2 из 3`, которое сохраняется после отказа одного участника. AWS описывает такую топологию для согласованной межрегиональной записи [24]. Все регионы обслуживают пользовательские запросы; дополнительные расходы на инфраструктуру принимаются ради устойчивости к региональной аварии [34].

### 3.4. Расположение регионов

Выбраны **Frankfurt, Paris и Milan** — три города в разных странах ЕС с существующими облачными регионами и поддержкой Multi-AZ [22].

| Город | AWS-регион | Основание выбора |
|---|---|---|
| Frankfurt | `eu-central-1` | Центральная Европа, крупный сетевой узел DE-CIX [27] |
| Paris | `eu-west-3` | близость к пользователям Западной Европы |
| Milan | `eu-south-1` | близость к пользователям Южной Европы |

Германия, Франция, Италия, Испания и Польша составляют около 66% населения ЕС [21]. Выбранные локации приближают региональные входные точки к значительной части этой аудитории, при этом основной объём фотографий доставляется через CDN.

По опубликованным измерениям CloudPing, RTT между Frankfurt и Paris составляет примерно **11 мс**, Frankfurt и Milan — **12 мс**, Paris и Milan — **19 мс** [26]. Это ориентиры сетевого обмена между регионами, а не гарантированное время ответа API. Такая география даёт разумный компромисс между разделением площадок и задержкой согласованной записи; удалённые регионы вроде Stockholm или Dublin увеличивают межрегиональные расстояния.

### 3.5. Общие данные и резервирование мощности

Каждый регион содержит **полную копию данных сервиса**; пользователи и анкеты доступны из любого региона. Запрос направляется в подходящую входную точку без закрепления пользователя за отдельным хранилищем.

Для профилей, геопозиции, реакций и Match выбирается согласованная межрегиональная запись: операция подтверждается после надёжного сохранения не менее чем в двух регионах. Размещение реплик должно сохранять кворум при потере любого одного региона [25]. Это обеспечивает **RPO = 0 для подтверждённых записей БД при отказе одного региона**. Отстающая реплика догоняет остальные; согласованное чтение учитывает это отставание. Проверка взаимности Like и создание единственного Match требуют транзакционной обработки, уникального ключа пары и идемпотентности запросов; детали относятся к проектированию БД.

Доли запросов между регионами определяются DNS-балансировкой по задержке и доступности. В исходных данных проекта отсутствуют измерения распределения аудитории по регионам и пользовательских сетевых задержек, поэтому фиксированные доли трафика не задаются.

При отказе одного региона его запросы переходят в оставшиеся. Для расчёта мощности API каждого региона принимается консервативная верхняя граница — **весь внешний пик ≈17 265 RPS**, рассчитанный в п. 2.6.6. Таким образом, любой регион способен принять полный поток, а резервирование не зависит от предполагаемых долей трафика. Распределение RPS между регионами для этого расчёта не требуется. Конфигурации и количество серверов определяются в последующих разделах.

Каждая полная реплика БД применяет изменения из всех регионов, поэтому нагрузка записи в хранилища также не уменьшается пропорционально локальному API-трафику. Межрегиональная репликация создаёт отдельный внутренний сетевой трафик.

### 3.6. DNS-балансировка

#### API

Для `api.example.com` используется **DNS-балансировка по задержке — Amazon Route 53 latency-based routing**. Провайдер выбирает регион с наименьшей оценочной задержкой из доступных [28]. Выбор зависит от DNS resolver и поддержки EDNS Client Subnet, поэтому географически ближайший регион не гарантируется.

```text
User -> DNS: api.example.com
                 |
          latency + health
           /     |     \
          v      v      v
      Frankfurt Paris  Milan
          |      |      |
       local load balancing / API
```

Региональные DNS-записи связаны с проверками готовности API и его доступа к БД. При недоступности региона он исключается из выбора; принимается TTL **60 секунд** [31]. Переключение учитывает время обнаружения отказа и DNS-кэширование. Распределение между AZ и backend-инстансами относится к локальной балансировке.

#### Media

`media.example.com` направляется на инфраструктуру CDN:

```text
media.example.com -> CDN provider
```

Далее выбор edge-узла выполняется Anycast/BGP-маршрутизацией CDN.

### 3.7. Anycast-балансировка media

```text
User
  |
  | DNS
  v
media.example.com
  |
  v
CDN Anycast IP
  |
  | BGP routing
  v
CDN edge / PoP
  |
  +-- cache HIT --> photo
  |
  +-- cache MISS --> available regional origin --> photo storage
```

При Anycast один IP-префикс анонсируется из нескольких точек CDN-сети. BGP направляет пользовательский трафик в выбранный PoP [30]. Географически ближайший PoP не гарантируется, поскольку результат зависит от peering, BGP-политик и traffic engineering [32].

Media origin и копии фотографий размещаются во всех трёх регионах. Для обращений CDN к origin используется Cloudflare Load Balancing с проверками доступности и порядком переключения **Frankfurt → Paris → Milan** [33]. Поэтому отказ Frankfurt не блокирует загрузку фотографий при cache miss.

Новая фотография публикуется после сохранения оригинала и подготовленных вариантов в двух регионах; третья копия пополняется асинхронно. Если выбранный origin ещё не получил объект, он получает его из доступной региональной копии. Согласование метаданных выполняется через общую БД.

Собственный Anycast для API не используется: выбор региональной входной точки выполняется DNS-балансировкой.

### 3.8. Механизм регулировки трафика между дата-центрами

В обычном режиме API-запросы распределяются по задержке. Отказ отдельной AZ обрабатывается локальной балансировкой, а отказ региона — исключением его входной точки из DNS-ответов. Проверка готовности должна учитывать возможность согласованной работы с БД, чтобы изолированный регион не продолжал принимать записи без кворума.

Для плановых работ регион исключается тем же механизмом готовности. Возврат выполняется после восстановления реплик и проверки работоспособности. Фактические доли трафика, задержки и загрузка регионов контролируются мониторингом.

При cache hit фотографии обслуживает CDN; при недоступности media origin провайдер выбирает следующий здоровый пул. Межрегиональная синхронизация данных работает независимо от пользовательской маршрутизации.

### 3.9. Итоговая схема

```text
                         EU-27 users
                        /           \
               api.example.com   media.example.com
                      |                 |
              DNS latency + health   CDN Anycast
                      |                 |
          +-----------+-----------+  cache / proxy
          |           |           |     |
      Frankfurt     Paris       Milan   |
       Multi-AZ    Multi-AZ     Multi-AZ |
          |           |           |     |
         API         API         API    |
          |           |           |     |
       DB copy     DB copy     DB copy  |
          \___________|___________/     |
             inter-region quorum       |
                                       v
                regional media origins + photo copies
```

Принятые решения:

- API обслуживается тремя активными регионами ЕС: Frankfurt, Paris и Milan;
- каждый регион содержит полный набор данных и использует Multi-AZ размещение;
- запись БД согласуется межрегиональным кворумом с устойчивостью к потере одного региона;
- DNS выбирает доступную входную точку по задержке;
- фотографии доставляются через CDN Anycast с резервированием региональных origin.

## 4. Локальная балансировка нагрузки

### 4.1. Схема балансировки

В каждом регионе используются два уровня:

- **L4 — распределение соединений** между доступными балансировщиками NGINX.
- **L7 — обработка HTTPS и распределение запросов** между серверами нужного сервиса: Discovery, Like/Pass, Location Update или Match List.

L4 работает в режиме TCP/443 и передаёт TLS-соединение в NGINX без расшифрования.

NGINX завершает защищённое HTTPS-соединение, чтобы серверы приложения занимались продуктовой логикой. Запрос передаётся серверу с наименьшим числом активных соединений — такой способ балансировки поддерживается NGINX [35]. Это учитывает разную длительность операций: формирование Discovery может занимать больше времени, чем сохранение реакции.

```mermaid
flowchart TD
    dns["Глобальная DNS-балансировка"] --> l4["Отказоустойчивый сетевой вход L4"]
    l4 --> nginxOne["NGINX — зона 1, L7 / HTTPS"]
    l4 --> nginxTwo["NGINX — зона 2, L7 / HTTPS"]
    l4 --> nginxThree["NGINX — зона 3, L7 / HTTPS"]
    nginxOne --> services["Серверы соответствующего сервиса в нескольких зонах доступности"]
    nginxTwo --> services
    nginxThree --> services
```

Сетевой вход L4 размещается в нескольких зонах доступности и исключает недоступные NGINX из распределения. Подобную возможность предоставляют облачные провайдеры, например AWS Network Load Balancer [36]. В проекте используется одна такая отказоустойчивая точка входа на регион.

Фотографии доставляются через CDN по схеме раздела 3 и обходят балансировщики API.

### 4.2. Расчёт количества балансировщиков

По п. 3.5 каждый регион должен принимать **полный внешний пик — 17 265 запросов/с**. Поэтому приведённые ниже пиковые нагрузки целиком закладываются в мощность каждого региона.

#### 4.2.1. Нагрузка на SSL/TLS-терминацию

Терминация включает установление защищённых соединений и шифрование/расшифрование передаваемых данных. Частоту новых соединений оцениваем в **SSL TPS — новых TLS-соединениях в секунду**, как в методике NGINX [38]. При повторном использовании соединений эта величина отличается от HTTP RPS.

Для базового сценария принимается **одно новое TLS-соединение с API на одно использование приложения**; последующие запросы этого использования идут по тому же соединению с keepalive.

По п. 2.2.2 число использований приложения в сутки:

`S_day = 15 млн × 52 / 30 = 26 млн`

Средняя частота установления соединений:

`H_avg = 26 млн / 86 400 ≈ 301 TLS-соединение/с`

Для частоты установления соединений принимается тот же суточный коэффициент `K_peak = 1,85`, что и для API:

`H_peak = 26 млн / 86 400 × 1,85 ≈ 557 TLS-соединений/с`

На одно использование приложения приходится в среднем `806,3 млн / 26 млн ≈ 31 API-запрос`. Повторное использование соединения в базовом сценарии уменьшает число TLS-handshake примерно в 31 раз по сравнению с отдельным соединением на каждый запрос.

Для выбора количества узлов используется **предельный сценарий: каждый API-запрос открывает новое TLS-соединение**. Выигрыш от повторного использования соединений и TLS session resumption в расчёт мощности не закладывается:

`H_max,peak = RPS_peak = 17 265 TLS-соединений/с`

| Сценарий | Новых TLS-соединений/сутки | Средний SSL TPS | Пиковый SSL TPS |
|---|---:|---:|---:|
| Базовый: одно соединение на использование приложения | 26 млн | ≈301 | ≈557 |
| Предельный: одно соединение на API-запрос | ≈806,3 млн | ≈9 333 | ≈17 265 |

Клиентский TLS для `media.example.com` завершается на CDN; эта нагрузка не относится к NGINX API. Шифрование/расшифрование данных API дополнительно учитывается через сетевую нагрузку и проверку совместной производительности ниже.

#### 4.2.2. Производительность узла и количество узлов

Верхняя граница сетевой нагрузки API — **8,76 Гбит/с** из п. 2.7.1. Это весь объём категории «Дополнительные фото + API/metadata + protocol overhead»; дополнительные фотографии также доставляет CDN, поэтому такая граница включает запас без назначения произвольной доли API-трафика.

В качестве ориентира берётся конфигурация из опубликованного руководства NGINX для физических серверов [37]:

| Параметр | Значение |
|---|---:|
| Процессор | 4 ядра Intel Xeon Platinum 8168 |
| Оперативная память | 8 ГБ |
| Сетевые интерфейсы | 2 × 10 Гбит/с |
| Новых защищённых соединений, SSL TPS (RSA) | 17 400 в секунду |
| Пропускная способность в тесте передачи данных | 8 Гбит/с |

SSL TPS получены с RSA-2048, шифром `ECDHE-RSA-AES256-GCM-SHA384` и OpenSSL 1.1.0g [37]. Для сети используется опубликованная производительность **8 Гбит/с**, а не номинальная скорость интерфейсов.

По обработке защищённых соединений:

`N_TLS = ceil(17 265 / 17 400) = 1`

По пропускной способности сети:

`N_network = ceil(8,76 / 8) = 2`

Следовательно, для обслуживания нагрузки нужны **`N = max(1, 2) = 2` балансировщика**.

SSL TPS измерены с ответом 0 байт, а пропускная способность — в отдельном HTTP-тесте с ответом 1 МБ [37]. Полученный расчёт задаёт начальную конфигурацию; одновременное установление TLS-соединений и шифрование/расшифрование потока данных проверяют нагрузочным тестом на выбранных версиях NGINX/OpenSSL и параметрах TLS.

### 4.3. Резервирование

Принимается схема **`N+1 = 2+1 = 3` балансировщика NGINX на регион**, по одному в каждой из трёх зон доступности. Все три работают одновременно. После отказа одного балансировщика или целой зоны остаются два: суммарно **34 800 новых защищённых соединений/с** и **16 Гбит/с** по опубликованным показателям. Это выше расчётной нагрузки региона по обоим ограничениям.

При равномерном распределении полного расчётного пика региона нагрузка на один NGINX составляет:

| Режим | Работающих NGINX | SSL TPS на узел, предельный сценарий | Доля SSL TPS узла от 17 400 | Сетевой поток на узел |
|---|---:|---:|---:|---:|
| Все узлы доступны | 3 | `17 265 / 3 = 5 755` | ≈33,1% | `8,76 / 3 = 2,92 Гбит/с` |
| Отказ одного узла или AZ | 2 | `17 265 / 2 ≈ 8 633` | ≈49,6% | `8,76 / 2 = 4,38 Гбит/с` |

Проценты показывают долю опубликованной производительности по установлению TLS-соединений; фактическую загрузку CPU при одновременной передаче данных определяет нагрузочный тест.

Проверки доступности исключают неисправный балансировщик или сервер приложения из распределения. Обновления выполняются по одному узлу, сохраняя необходимую мощность. Если недоступен весь регион или он потерял доступ к БД, запросы перенаправляются в другие регионы по правилам раздела 3.

Всего для Frankfurt, Paris и Milan требуется **9 балансировщиков NGINX и 3 отказоустойчивые сетевые точки входа L4**. Внутреннее резервирование управляемого L4 обеспечивает провайдер; число NGINX рассчитано отдельно выше.
